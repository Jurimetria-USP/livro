10  Um exemplo integrado do ecossistema

R, Python, Positron, Quarto, Git e agentes em um projeto jurídico

Autores

Alexandre Nicolella

José de Jesus Filho

10.1 Introdução

Os capítulos anteriores apresentaram as ferramentas separadamente. Este capítulo reúne seus papéis na criação de um projeto colaborativo iniciado em uma pasta vazia. O percurso começa no Positron, cria um repositório Git local, registra as primeiras versões, publica o repositório no GitHub e incorpora um colaborador. Depois, Codex ou Claude Code auxiliam na montagem dos arquivos do projeto sob supervisão humana.

Utilizaremos dados ilustrativos de três estados brasileiros sobre homicídios de mulheres e feminicídios. Os valores servem apenas para acompanhar o fluxo computacional e não devem ser interpretados como uma análise substantiva do fenômeno.

NotaObjetivos do capítulo

Ao final deste capítulo, você deverá ser capaz de:

  • criar uma pasta de projeto e abri-la como raiz no Positron;
  • iniciar um repositório Git local pela interface do Positron;
  • criar README.md, .gitignore e AGENTS.md;
  • registrar um primeiro commit local;
  • publicar o repositório no GitHub e convidar um colaborador;
  • distinguir commit local, envio, recebimento e sincronização;
  • abrir Codex ou Claude Code no contexto da pasta;
  • executar um script de R que produz uma base;
  • utilizar Python para verificar o arquivo produzido;
  • renderizar um relatório Quarto;
  • registrar uma nova etapa sem misturar mudanças não relacionadas.

10.2 O percurso do exemplo

O trabalho parte de uma pasta vazia. A estrutura inicial é registrada localmente antes da publicação no GitHub. Somente depois dessa base organizacional criamos códigos, dados e relatório.

10.3 Antes de começar

Este capítulo pressupõe que as etapas anteriores foram concluídas. O computador já deve possuir Git, R, Python, Positron e Quarto. Também são necessárias uma conta no GitHub e a extensão do Codex ou do Claude Code instalada no Positron. Não será necessário instalar novamente essas ferramentas.

10.4 Etapa 1 — Criar e abrir a pasta

Crie uma pasta chamada exemplo-juridico em um local destinado aos projetos da disciplina. No Positron:

  1. selecione File > Open Folder;
  2. localize exemplo-juridico;
  3. selecione Select Folder;
  4. confirme que EXEMPLO-JURIDICO aparece no primeiro nível do Explorer.

Nesse momento, a pasta pode estar vazia. Abrir a pasta no Positron define a raiz utilizada pelo Explorer, pelo terminal, pelo Git e pelos agentes.

AvisoAbra somente a pasta do projeto

Não abra como raiz uma pasta ampla que contenha outros trabalhos. O Git e os agentes devem atuar apenas dentro de exemplo-juridico.

10.5 Etapa 2 — Iniciar o Git local

Na barra lateral do Positron, selecione o ícone Source Control. Como a pasta ainda não possui Git, o painel apresentará o botão Initialize Repository. Selecione esse botão.

O Positron executará a inicialização do Git na pasta aberta. O procedimento cria a pasta oculta .git, que contém o histórico local. Ele não cria um repositório no GitHub e não envia nenhum arquivo à internet.

NotaO que não é criado automaticamente

Initialize Repository não cria README.md, .gitignore ou AGENTS.md. Esses documentos pertencem ao conteúdo do projeto e serão criados nas etapas seguintes.

Se o botão não aparecer, confirme se a pasta correta está aberta e se o Git foi reconhecido. O terminal pode ser usado apenas para diagnóstico:

git status

10.6 Etapa 3 — Criar os primeiros arquivos

No Explorer, selecione o botão New File e crie, um por vez, README.md e .gitignore.

No README.md, registre:

# Exemplo jurídico integrado

Projeto didático para demonstrar a organização de uma pesquisa jurídica
com Git, GitHub, Positron, R, Python, Quarto e agentes de inteligência
artificial.

Os dados utilizados neste exemplo são ilustrativos.

No .gitignore, indique arquivos locais que não devem ser versionados:

.Rhistory
.RData
.Ruserdata
.venv/
.env

Salve os dois arquivos. O painel Source Control deverá mostrá-los como alterações ainda não registradas.

10.7 Etapa 4 — Fazer o primeiro commit local

No painel Source Control:

  1. examine os arquivos apresentados em Changes;
  2. selecione o sinal + ao lado de cada arquivo para incluí-lo em Staged Changes;
  3. escreva a mensagem Cria a estrutura inicial do projeto;
  4. selecione Commit.

Esse commit registra a primeira versão no computador. Ele ainda não foi enviado ao GitHub.

10.8 Etapa 5 — Publicar o repositório no GitHub

Depois do primeiro commit, o painel Source Control pode apresentar Publish Branch ou Publish to GitHub. Selecione a opção disponível e:

  1. autentique sua conta do GitHub, se solicitado;
  2. confirme o nome exemplo-juridico;
  3. escolha se o repositório será público ou privado;
  4. confirme a publicação;
  5. abra o endereço indicado e confira README.md e .gitignore.

Essa operação cria o repositório remoto, associa-o ao repositório local e envia o histórico existente. Publicar o repositório não significa publicar uma página; GitHub Pages constitui outra decisão.

10.9 Etapa 6 — Convidar um colaborador

Na página do repositório no GitHub:

  1. abra Settings;
  2. na seção Access, escolha Collaborators;
  3. selecione Add people;
  4. pesquise o nome de usuário exato do colaborador;
  5. envie o convite.

O colaborador somente terá acesso depois de aceitar o convite. Cada participante utiliza sua própria conta; senhas e códigos de autenticação não são compartilhados.

10.10 Etapa 7 — Obter o projeto no computador do colaborador

Depois de aceitar o convite, o colaborador abre o Positron sem uma pasta de projeto e escolhe New Folder from Git. Em seguida, informa o endereço do repositório, escolhe onde salvar a cópia e abre a pasta criada.

Esse procedimento realiza um clone: cria uma cópia local com os arquivos e o histórico existentes no GitHub. A partir daí, cada participante trabalha em sua própria cópia e troca versões pelo repositório remoto.

10.11 Etapa 8 — Abrir o agente no projeto

Com exemplo-juridico aberto no Positron, abra o painel do Codex ou do Claude Code. A extensão utilizará a pasta aberta como contexto local. O primeiro pedido deve ser de leitura e proposta:

Examine README.md e .gitignore. Não altere arquivos e não execute comandos. Proponha uma estrutura mínima para um projeto jurídico didático que utilizará R, Python e Quarto. Explique a função de cada pasta e aguarde aprovação.

Depois de revisar a proposta, autorize apenas a estrutura aprovada. Um resultado possível é:

exemplo-juridico/
├── dados/
├── scripts/
│   ├── criar_dados.R
│   └── verificar_dados.py
├── AGENTS.md
├── .gitignore
├── README.md
└── relatorio.qmd

10.12 Etapa 9 — Criar as orientações do agente

Crie AGENTS.md pelo botão New File ou autorize o Codex a criá-lo com o conteúdo aprovado:

# Orientações do projeto

Este é um projeto didático de análise de dados jurídicos.

- Leia o README antes de propor alterações.
- Não modifique arquivos sem autorização expressa.
- Não execute Git nem publique arquivos.
- Não invente dados, fontes ou resultados.
- Preserve os exemplos aprovados.
- Depois de cada alteração, informe exatamente o que mudou.

O AGENTS.md orienta o Codex quando ele trabalha nessa pasta. Se o projeto também utilizar Claude Code, as orientações comuns podem ser adaptadas em CLAUDE.md. A elaboração de regras mais completas será retomada na Parte III.

AvisoExemplo distinto de uma estrutura definitiva

Esta organização foi reduzida para tornar visível a integração das ferramentas. O projeto de uma pesquisa real exigirá pastas, documentação, regras e procedimentos adicionais.

10.13 Etapa 10 — Produção da base em R

No arquivo scripts/criar_dados.R, registre:

# Dados ilustrativos de três estados brasileiros

estados <- c("Acre", "Alagoas", "Amapá")
homicidios_mulheres <- c(22, 73, 22)
feminicidios <- c(11, 31, 8)

dados_crimes <- data.frame(
  estado = estados,
  homicidios_mulheres = homicidios_mulheres,
  feminicidios = feminicidios
)

write.csv(
  dados_crimes,
  "dados/dados_crimes.csv",
  row.names = FALSE,
  fileEncoding = "UTF-8"
)

dados_crimes

O script reúne os vetores em um data.frame e grava o resultado em dados/dados_crimes.csv. O caminho parte da raiz do projeto.

Com o arquivo aberto no editor, execute o script em uma sessão de R. Depois, confirme no Explorer que a pasta dados/ contém o CSV.

10.14 Etapa 11 — Verificação em Python

No arquivo scripts/verificar_dados.py, utilize apenas a biblioteca padrão do Python:

import csv
from pathlib import Path

caminho = Path("dados") / "dados_crimes.csv"

with caminho.open(encoding="utf-8-sig", newline="") as arquivo:
    linhas = list(csv.DictReader(arquivo))

colunas_esperadas = {
    "estado",
    "homicidios_mulheres",
    "feminicidios",
}

if not linhas:
    raise ValueError("A base não contém observações.")

colunas_encontradas = set(linhas[0].keys())

if colunas_encontradas != colunas_esperadas:
    raise ValueError(
        f"Colunas encontradas: {sorted(colunas_encontradas)}"
    )

print(f"Arquivo verificado: {caminho}")
print(f"Número de observações: {len(linhas)}")

No terminal da raiz, execute:

python scripts/verificar_dados.py

O Python não recria a análise. Ele realiza uma verificação independente e pequena: confirma que o arquivo existe, contém observações e possui as colunas esperadas.

10.15 Etapa 12 — Relatório em Quarto

No arquivo relatorio.qmd, insira:

Este relatório apresenta uma base ilustrativa utilizada para demonstrar a

Os valores são ilustrativos e não sustentam inferência sobre os estados.

No terminal da raiz, renderize:

quarto render relatorio.qmd

O arquivo relatorio.html será criado ao lado da fonte, salvo se uma configuração de projeto determinar outro diretório.

10.16 Etapa 13 — Observar o projeto no Positron

Ao final das etapas anteriores, o Explorer deve mostrar os arquivos-fonte e os resultados produzidos. A sessão de R pode apresentar dados_crimes no painel de objetos, enquanto o terminal registra a verificação do Python e a execução do Quarto.

Observe que nenhum desses painéis é o projeto. O projeto é a estrutura de arquivos preservada no computador. Objetos existentes apenas na memória desaparecem quando a sessão é encerrada; por isso, as operações necessárias devem permanecer nos scripts.

10.17 Etapa 14 — Registrar a nova etapa

Retorne ao painel Source Control. Examine separadamente os novos arquivos e confirme que .venv, históricos de sessão e credenciais não aparecem na lista. Depois:

  1. selecione os arquivos correspondentes ao exemplo;
  2. escreva a mensagem Adiciona o primeiro exemplo integrado;
  3. selecione Commit;
  4. selecione Sync Changes ou Push para enviar o novo commit ao GitHub.

O commit registra a versão local. Push envia os commits locais ao GitHub. Pull recebe commits existentes no remoto. Sync Changes combina o recebimento e o envio previstos pela interface.

Antes de começar uma nova etapa, cada participante deve receber as mudanças já compartilhadas. Antes de enviar, deve revisar seus próprios arquivos e criar um commit coerente. Quando duas pessoas alteram a mesma parte de um arquivo, o Git pode solicitar a resolução de um conflito; essa resolução exige comparar as versões e decidir qual conteúdo deve permanecer.

10.18 Etapa 15 — Revisão de leitura por um agente

Com os arquivos criados, um agente pode receber um pedido delimitado:

Leia README.md, scripts/criar_dados.R, scripts/verificar_dados.py e relatorio.qmd. Não altere arquivos, não execute comandos e não use Git. Verifique se os nomes das colunas, os caminhos e a finalidade declarada são consistentes. Relate os problemas encontrados e apresente propostas para aprovação.

O pedido identifica os arquivos, limita as ações e define o resultado esperado. Se o agente sugerir uma correção, a mudança deve ser examinada antes de nova autorização.

10.19 Como as ferramentas se complementam

Elemento Função no exemplo
R cria a base e realiza o cálculo
Python verifica a estrutura do CSV
Positron reúne arquivos, sessões e terminal
Quarto combina explicação, código e resultado
Git registra versões locais do projeto
GitHub compartilha o histórico entre os colaboradores
agente propõe, cria e revisa arquivos dentro do escopo autorizado

Não é necessário utilizar duas linguagens em toda pesquisa. O exemplo usa R e Python para demonstrar que o ambiente pode integrá-las. A escolha deve decorrer da necessidade metodológica e da possibilidade de manter o trabalho compreensível.

10.20 Síntese

O exemplo começou em uma pasta vazia, criou um repositório local, registrou um primeiro commit, publicou o histórico no GitHub e incorporou um colaborador. Em seguida, um agente apoiou a estruturação aprovada, R produziu os dados, Python verificou sua estrutura e Quarto gerou o relatório. A etapa final registrou e sincronizou o novo resultado.

Nos capítulos seguintes, essa estrutura será ampliada para um projeto de pesquisa. Passaremos da demonstração técnica para a definição das fontes, das regras de trabalho, da coleta, da extração e da organização do banco de dados.
